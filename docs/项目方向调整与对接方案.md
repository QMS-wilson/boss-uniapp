## 二、真实后端契约（必须以此为准）

### 2.1 响应信封

文档第 45 章明确写道：

> 线上返回 envelope 为 `{ok, data|error}`，不是 2.3 节的 `{success,data}`。

```json
// 成功
{ "ok": true, "data": {...} }

// 失败
{ "ok": false, "error": { "code": "AGENT_OFFLINE", "message": "..." } }
```

**本项目当前用的是 `{ ok, data, code, message }`** —— 成功分支对，失败分支结构错（真实是嵌套在 `error` 里）。这是接后端第一秒就会踩的坑。

### 2.2 鉴权头

```http
Authorization: Bearer <accessToken>
X-Store: <店铺 name>     ← 注意是 name，不是 id
Content-Type: application/json
```

**本项目当前发的是 `X-Store: <当前店铺 id>`** —— 真实后端要求传店铺 **name**。
另外旧链路需要 `X-Openid`，新链路（accessToken）不需要。

本项目当前用的是 `from` / `to`（`monthRange()` 返回的），**两者都不匹配**。

### 2.5 取价规则（真实远比本项目复杂）

`D:\v3-wechat\v3agent\price.py` 的实现：

1. `PriceTrace=201` 时，查 `Price_Kh` 表该客户+货品+单位的最近销价（**优先同单位，其次任意单位**），取 `D_PriceTax` 字段
2. 回退到默认价：`HpdanUnit` 单位档案 → `Hpdan` 货品档案的 `D_SJ1` 列（本账套 98% 价格在此列）
3. 仍无 → `price=0, manual=true`

返回结构：`{price, source, unit, rate, recent: {bill_no, sale_date}, manual}`

**本项目 `utils/price.js` 的实现缺陷**：
- 用 `salePriceDefault` / `recentSalePrice` 字段，真实是 `D_SJ1` 和 `Price_Kh` 表
- `rate`（换算率）字段缺失 —— 多单位场景必须要
- `recent` 里没有单据号和历史日期，用户看不到"这个价是哪张单的"
- 而且 mock/router.js 里还有**第二套**更简化的实现（见第三节风险 3）

### 2.6 改单约束（真实有 11+ 条，本项目只做了 5 条）

`D:\v3-wechat\v3agent\sales.py` 的 `editable_reasons()`：

| 真实条件 | 本项目是否覆盖 |
|---|---|
| `bill_state != 0`（作废/红冲） | ❌ 缺 |
| `ISOK=0` | ❌ 缺 |
| `is_auditing`（已审核） | ✅ |
| `is_receive`（已收款） | ✅ hasPayment |
| `is_send`（已发送） | ❌ 缺 |
| `shipped`（已发货） | ✅ hasShipment |
| `reconcile_time`（已对账） | ✅ hasReconcile |
| `auditing_time`（已有审核时间） | ❌ 缺 |
| `time_void` / `user_void`（已作废） | ❌ 缺 |
| `j_jefk` 等 5 个金额字段非 0（收款/结算金额） | ❌ 缺 |
| 明细 `jh_order_no`/`link_pick_no`/`s_depufin`/`s_thsl`/`link_xs_bill_guid` 关联 | 部分（hasLinkage） |

**风险**：本项目 UI 可能给一张实际不可改的单据显示"修改"按钮，用户点进去保存时才被后端 409 拒绝。
体感是"这软件有 bug"，实际是前端校验不全。

**推荐做法**：不要在前端重实现这套规则。真实后端 `bill.get` **已经返回 `editable` 和 `editable_reasons[]`**，前端直接消费即可。
前端只保留 UI 兜底（如已审核单不显示修改按钮）。

### 2.7 新建/改单的 body 结构

**新建**（真实）：
```json
{
  "customer": "K01094",
  "lines": [{ "hpbh": "60108183", "unit": "支", "qty": 1, "price": 3.5 }],
  "ndate": "2026-09-18",
  "warehouse": "101-",
  "note": "备注"
}
```
注意：`customer` 是**客户编号字符串**，不是 `customerId`；`lines` 里用 `hpbh`。
`price` 可省略 —— 省略时后端按客户取价规则自动算。

**改单**（真实，PUT）：
```json
{
  "header": { "NDate": "2026-09-05 00:00:00", "ItemBh": "K01094", "BZ_XS": "备注" },
  "lines": [
    { "iden_guid": "...", "hpbh": "101025", "unit": "张", "qty": 12, "price": 3.0 },
    { "hpbh": "60108782", "unit": "支", "qty": 15 }
  ]
}
```

**这是最危险的一处**：`lines` 必须提交该单**最终完整明细**。
带 `iden_guid` = 保留/修改原行，不带 = 新增，**未提交的原行会被删除**。
本项目当前是 `items.map(...)` 全量提交但**不带 `iden_guid`** —— 提交后会变成"删掉所有旧行、全部插新行"，
虽然业务结果可能一致，但会丢失行级身份，且触发器的关联校验可能误判。必须补上。

## 三、本项目自身的三个硬伤（与后端无关，独立存在）

### 硬伤 1：离线降级是空转的

`src/api/salesBill.js`：

```js
function checkOnline() {
  // 简单判定：uni.getNetworkType 同步不可得，这里用上次请求结果兜底；
  // request 层网络失败时已走离线分支。此处默认 true，由 request 层兜底。
  return true
}
```

注释声称"由 request 层兜底"，但 `request.js` 的网络失败分支**只返回错误对象，不写草稿**。
所以 `if (!online)` 永远不成立，`cache.addDraft()` 永远不执行。
`store/cache.js` 里精心写的 `addDraft / flushDrafts / hasDrafts` 全是死代码。

**后果**：仓库没信号时，销售员填完 20 行单据点保存 → 报"网络连接失败" → 全部白填。

**修法**：删除 `checkOnline`，改为在 `request` 层的网络失败分支里对写操作落草稿：

```js
catch (e) {
  if (offlineOk && cacheKey) { /* 读操作返回缓存 */ }
  if (isWrite && opts.draftType) {
    cache.addDraft(opts.draftType, opts.draftPayload ?? data)
    return { ok: true, offline: true, draft: true, message: '当前离线，已存为草稿' }
  }
  return _err('NETWORK_ERROR', '网络连接失败')
}
```

### 硬伤 2：token 刷新可能自己调自己

`store/auth.js` 的 `maybeRefresh()` 走的是 `http.post('/auth/refresh')` —— 经过 401 拦截器。
而拦截器收到 401 时又去调 `_refreshToken` 刷新。若 refreshToken 也过期，这条链路会绕圈。

对比参考：`miniapp/utils/request.ts` 的 `agentRpc()` 里，refresh 调用也是走 `request()`，
但它的退出条件是 `if (!s.refreshToken || code !== 'TOKEN_INVALID' ...) throw e`，靠**明确的 code 判断**兜住。
本项目 `request.js` 的 `_refreshToken` 用的是**裸 `uni.request`**（正确），但 `auth.maybeRefresh()` 绕过了它。

**修法**：抽出 `refreshRaw(refreshToken)` 用裸请求，`_refreshToken` 和 `maybeRefresh` 共用。

### 硬伤 3：取价规则有两套实现，结果会不一致

- `utils/price.js` 的 `resolvePrice()` —— 支持多单位（`units[]` 里按 unit 匹配）
- `mock/router.js` 的 `resolvePriceMock()` —— **完全无视 `unit` 参数**，只读商品级字段

而 `pages/sales/edit.vue` 调的是 mock 那条路。同一张砂纸按"张"卖（1.5）和按"包"卖（70），取价逻辑不一样。
mock 里那份是重复实现，应直接 `import { resolvePrice }` 删掉。

## 四、方向调整建议

### 4.1 定位重新校准

本项目 README 写的是"进销存移动经营管理端"，页面里出现了**进销存全模块**的架子（销售/客户/商品/库存/报表/打印/我的）。
但真实后端的能力边界是明确的：

**后端已支持（可以真做）**：销售单查/建/改、客户查/建/改、商品查/建/改价、库存查询、取价、看板、6 类报表、客户对账单、远程打印、审计日志、异步任务。

**后端不支持（做了也没数据）**：
- ❌ **采购模块** —— 老板端 `App.tsx` 里 Purchase / PurchaseDetail / PurchaseForm 明确写着"当前接口暂未提供采购单列表/详情"，是**空壳**。本项目不要跟进去做。
- ❌ **收款单/付款单** —— 文档第 9 节：「后续如客户开始录收款，需要把 XSSK/KHXSSK 收款单并入对账单」。当前**没有**收款录入接口。
- ❌ **退货/红冲** —— README Roadmap 第 4 条列为未完成。
- ❌ **多单位换算（rate≠1）** —— README 明确「多单位（换算率≠1）暂不支持，会明确报错」。
- ❌ **打印格式自定义** —— 真实只暴露"送打印"能力，不暴露格式编辑 REST。

**建议**：把本项目定位收窄为 **"销售移动端"**，与 `miniapp` 的能力集对齐，而不是铺"进销存"全模块。
当前 `pages/print/index.vue` 做的"格式列表 + 打印机选择"，真实后端不通过 REST 暴露，
应该改成调用 `/api/v1/print/salesbill` 直接送印，用 `/api/v1/capabilities` 展示可用打印机。

## 六、需要你确认的三个决策点

### 决策 1：本项目与现有小程序/老板端的关系？

三个客户端（原生小程序、React 老板端、本项目 uni-app）能力高度重叠。选项：

- **A**：本项目作为唯一多端入口，逐步替代另两个（成本最高，但只维护一套）
- **B**：本项目专注"销售员现场作业"场景（开单/改单/扫码/离线），另两个做老板看数据
- **C**：本项目仅作为技术验证，不投产

**建议 B**。理由：本项目已在"改单状态机 + 离线草稿 + 取价可追溯"上做了深度设计，这些正好是**销售员跑现场**的痛点；
而老板端看板/报表用 H5 更合适。差异化定位能避免重复投入。

### 决策 2：是否保留离线草稿能力？

真实后端是"云端 → 本地 Agent → SQL Server"三段链路，任一段断都失败。
离线草稿在技术上可行（本地暂存，联网后 `flushDrafts` 上传），但有**订单重复提交**风险：
用户断网存草稿，恢复网络前又在别的端开了同一单，flush 时会产生重复单据。

- **A**：做，但 flush 前先查单据列表去重
- **B**：做，但只在创建时允许草稿（改单不允许，因为改单需要 `iden_guid` 快照，离线期间服务端可能已变）
- **C**：不做，断网时明确提示"请等待网络恢复"

**建议 B**。创建草稿安全（单号由服务端生成，不存在冲突），改单草稿危险（可能覆盖他人修改）。

### 决策 3：取价逻辑放前端还是后端？

- **A**：前端调 `/api/v1/price` 取价（当前架构）
- **B**：前端不传 price，让 `salesbill.create` 时后端按规则算

**建议 B 为主**：真实 `salesbill.create` 的 `lines` 允许省略 `price`（README 第 169 行注释："不给价=按客户取价规则"）。
前端调 `/api/v1/price` 只用于**展示**参考价给用户看，用户改价后显式传 price。
这样能保证"最终成交价"的判定权和桌面端 V3 一致，避免前端算出不同的价。
