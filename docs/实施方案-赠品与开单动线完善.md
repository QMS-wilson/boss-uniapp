## §1 明细赠品（`Gifts`，1=是 / 0=否）

### 1.1 现状
| 层 | 事实 |
|---|---|
| 库 | `XSMX.Gifts` / `JHMX.Gifts` bit NOT NULL 默认 0；两本账 0 行用到 |
| Agent 读 | 采购已有：`purchase.py:160` SELECT 带 `ISNULL(m.Gifts,0)` → `:187` `"gift": bool(r[17])`。**销售没有**：`sales.py:119-127` 的 `_load_lines` 不取这一列 |
| Agent 写 | 采购 `purchase.py:646` 的 INSERT 列里有 `Gifts`，但 VALUES 给的是**常量 0**（15 个占位符里没有它）⇒ 读得出、写不进。销售 INSERT(`:555-568`) 连列都没带 |
| 云端 | 明细是整包转发（`business.py` 不逐字段裁 lines），加一个键不用改云端 |
| 前端 | `utils/adapt.js` 明细映射里没有 gift；开单页明细行是 品名+单位胶囊+删除(`sales/edit.vue:98-107`) / **规格行 `:108`** / 数量·单价·金额(`:109-122`)；提交 payload `price: Number(it.price)`(`:1165`,`:1186`) |

### 1.2 目标行为
规格那一行右侧加一颗「赠品」开关（与单位胶囊同一行高、同一套自绘控件），点一下切 0/1；
切成功后这一行的视觉要**看得出来**（不是只有按钮变色）；提交时带 `gift: 1|0`；
草稿、详情、列表筛选都认得它。

### 1.4 边界与坑
- **bit 与 NULL**：读侧一律 `ISNULL(m.Gifts,0)`；写侧只准传 0/1 整数，别传 `true/false`
  （pymssql 会把 Python bool 写成 1/0，但走 JSON 的断网草稿重放会带 `true` ⇒ 触发 8114 类型转换错）。
- **老包兼容**：Agent 不升级、前端先发 ⇒ payload 里的 `gift` 被 Agent 忽略，功能静默不生效。
  所以**上线顺序必须 Agent 在前、前端在后**（与打印/多单位那几轮同一条）。
- **断网草稿**：`*.create` payload 里存的是提交形状，重放时 `gift` 必须还在 ——
  `check-draft-box.js` 那套"payload 形状"断言要补一条。
- **不改合计口径**：本轮**只加标记**，`calcTotal` / `J_JE` / 头表金额一律不动。
  合计要不要剔赠品是 1.6 的事，别混在一次改动里（混了就说不清数字为什么变了）。

### 1.5 验收
- 静态门（扩 `check-draft-box.js` 或新开 `check-bill-gift.js`）：
  Agent 两侧 SELECT/INSERT 都带 Gifts、前端四层（adapt 读/写、draftFormShape、detail 显示）都有 gift、
  写侧只出现 0/1。
- 实况门 `check-bill-gift-live.js`：开单页勾赠品 → 提交 → 读回详情 `gift=true` →

- 真库只读核：`数据库解构/probe-gifts.py`（本轮新写，跑 SELECT）在测试单提交后应打出

### 1.8 赠品会不会把客户的「最近价」改掉（只读探针实测，2026-10-03）

`probe-gift-bill.py` 新加了一段读 `Price_Kh`（这个客户在样本单之后的价格行）：

| 货品/单位 | D_Price | D_PriceTax | D_PriceZK | 来源单 |
|---|---|---|---|---|
| 02 / 件（正常行） | 72.00 | 72.00 | 72.00 | **XK00000003** |
| 02 / 个（**赠品行**） | 6.00 | 6.00 | **0.00** | （空） |

⇒ V3 的触发器**照写价格行、但不给赠品行落 `LastSaleBillNo`**，而 `D_PriceZK` 是按
`折后金额 ÷ 数量` 算的，赠品那就是 0。我们这边两条取价链路（`price.py:115/125`、`product.py:645`）
都带 `AND LTRIM(RTRIM(ISNULL(LastSaleBillNo,''))) <> ''` ⇒ **赠品的 6 块钱不会被当成这个客户的最近价**。
关键是这条**不用我们写代码**：我们写进 `XSMX` 的那几列与 V3 手录的逐列同形（见 1.7），
触发器是库里同一套，所以它给的 `Price_Kh` 结果也必然同形 —— 这段探针就是在核对这个前提。

顺带一条对界面的影响：客户 `201 最近销价` 方案下，**赠品行不改变下一次开单的取价**，
所以"送过一次之后这货变成 0 元"那种担心不会发生。

`J_JEZKE` 这一列不是"第二份金额"——`probe-jezke.py`（本轮新写，只读）按制单人分组量了两本账：

| 账套 | 明细行 | `J_JEZKE=0` | `J_JEZKE=J_JE` |
|---|---|---|---|
| `tongda`（客户真账的本地副本） | 95,987 | 95,987 | 0 |
| `geshi`（用户的赠品样本） | 7 | 6 | **1（就是那行赠品）** |

⇒ 厂商只在"钱被折掉/送掉"的那一行填它。**我们原来整列没写**，结果是：
手机开的赠品单在 V3 里查不出"这批送出去的货值多少钱"（合计/应收不受影响，
头表四个 SUM 读的是 `J_JEZK/J_JEHS/J_JE`）。已按实测补上：**赠品行 `J_JEZKE=货值`、正常行留 0**，
销售与采购两条 INSERT 同形（采购侧目前没有 V3 手录的赠品单可对，是同形推断，注释里写明了）。
`verify-gift.py` 加了 6 条真库断言（样本两条 + 我们写的赠品/正常行两条 + 改单取消后归零一条 + 采购侧一条），
现在 **30/0**；静态门也钉住了列序与规则（摘掉 `%s` 会当场红，已反证），现在 **37/0**。

★ 顺带把"往长 SQL 里插一个 `%s`"这类改法的门补上了：`进销存-本地Agent源码/scripts/check-insert-shape.py`
用 AST 把 INSERT 的**列数==值数、占位符数==实参数**查一遍，并按位置打印"哪一列 ← 哪个变量"。
只数 `%s` 是不够的 —— 错位一位时占位符一样多，`单价`会被写进`成本`列且不报语法错。
本次输出：`J_JEZK ← amt_zk`、`J_JEZKE ← amt_zk_e`、`J_JEHS ← amt_zk`、`Gifts ← 1 if gift else 0`，两侧都对。

## §8 开单那句库存提示：拆成四种说法 + 做成配置项（2026-10-03 用户提）

用户问的是「为什么有的明细会显示库存差 1 支 1 桶之类的」，量完现网才发现老算法在骗人：

**老写法只有一句**：`数量 × 倍率 − 账面 > 0` ⇒ 「库存差 N 基本单位」。三种情况被这一句冒充：

| 真实情况 | 现网实测（`shiwantongda`） | 老写法说 | 该说 |
|---|---|---|---|
| 从没入过库（`Inventory` 里没行） | 货品档案 **48,591** 个，库存表里只有 **211** 个 ⇒ 绝大多数是这种 | 「库存差 1 个」＝像欠货 | 这货品还没有库存记录 |
| 账面是负数 | 那 211 个里 **191 个为负**（防水胶圈 −312、油石 −105…） | 「库存差 313 个」＝虚高到吓人 | 账面 −312 个，库存数字不对 |
| 真不够 | — | 对 | 还差 N 支（账面 M 支） |
| 够 | — | 不出声 | 不出声 |

**单位为什么会出现"1 支 1 桶"**：提示一律折算到**基本单位**再比（不折算会出现"填 3 包、账面 320 支 ⇒ 说够"，
倍率 10 时实际要 30 支）。这行按 桶 开、账面按 支 记，所以同一行上两个单位并存 —— 现在把换算一起说了：
`还差 1 支（账面 11 支，1 桶 = 12 支）`。

**改动**
- 新增 `src/utils/stockHint.js`（纯函数，不碰 uni/storage）：四种分支 + 三态 `stockRecord`。
  ★ 抽出来是为了能被 Node 门**真调**——这类"分支判断"扫字符串一条都判不出来。
